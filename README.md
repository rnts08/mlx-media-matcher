# Media Match

Local photo-library analyzer built on Apple's MLX. Point it at a folder and it
builds an index that lets you:

- **find photos by person, object or free text** — CLIP vector search by
  default, caption/keyword search optionally
- **identify duplicates across resolutions** — accidentally saved thumbnails,
  WebP conversions and recompressed copies are grouped with their
  full-resolution primary file
- **group semantic near-duplicates** — e.g. several different shots of the
  same subject
- **refine tags into a clean vocabulary** — keywords are lowercased,
  singularized and synonym-merged into canonical tags, then bucketed into
  facets (person/scene/object/food/…); each photo is also *typed*
  (selfie/portrait/group/scene/city/animal/object/food/document/art) with
  zero-shot CLIP (`classify`)
- **group photos of the same person** — photos tagged with the person facet are
  clustered by CLIP similarity; name a cluster ("Alice") and list it with one
  command
- **mark the best version** — the largest image in every group is the primary

Everything runs locally: no cloud services, no PyTorch. Requires Apple Silicon.

## Status

- **Phase 1 (images): implemented** — described below.
- **Phase 2 (video): implemented** — the same capabilities for video files:
  keyframes sampled at ~1 fps, embedded with CLIP for search, and matched by
  keyframe pHash for duplicate/re-encode grouping (see `docs/video-spike.md`).
- **Tag refinement, image types & people clustering: implemented** —
  `describe` captions the media, `classify` types each photo, and `refine`
  turns captions into canonical tags/facets; `analyze` runs all of them in one
  pass. `people` clusters person photos and supports naming them.
- **Phase 3 (audio): inventory only** — `bootstrap` recognizes music/audio
  extensions and keeps them with `--media-only`, but audio is not scanned,
  fingerprinted, transcribed or deduplicated yet. The design and TODO seams are
  in [`docs/FEATURE-audio.md`](docs/FEATURE-audio.md).

The full command/operation map, including the command-vs-argument decisions, is
[`docs/CLI-LOGIC-MAP.md`](docs/CLI-LOGIC-MAP.md).

## Install

```bash
python3 -m venv .venv
.venv/bin/pip install -e .
```

Video support also needs `ffmpeg`/`ffprobe` on `PATH` (e.g. `brew install ffmpeg`).

Models are downloaded from Hugging Face on first use: CLIP ViT-B/32
(~600 MB) for `scan`, SmolVLM-256M (~150 MB) for `describe`/`analyze`.

## How it works

Each image is indexed by three complementary layers (see `docs/clip-spike.md`
for the measurements that justify the design):

| Layer | Engine | Purpose |
|---|---|---|
| CLIP embeddings | `mlx-community/clip-vit-base-patch32`, pure MLX, ~500 img/s, 2 KB/image | default search engine; text→image queries, image→image similarity (`similar`) |
| Perceptual hashes (pHash) | 64-bit DCT hash, no model needed | exact duplicate detection, resolution- and re-encode-independent; stays exact for tiny thumbnails where CLIP degrades |
| Vision-model captions (optional) | `mlx-community/SmolVLM-256M-Instruct-4bit`, ~1 s/image | human-readable descriptions + keywords for `search --fts` and `tags`; generated by `describe` or `analyze`, and only on the best version of each duplicate group |

The index lives in `<root>/.media-match.db` (SQLite + FTS5). Read-only
commands never create it — run `scan` first.

**Scanning is a four-stage pipeline**, not a loop. Raw file bytes are read by a
small pool of reader threads into a bounded ~1 GB ring buffer; CPU workers pull
from that buffer to decode, hash and preprocess; one GPU stage turns the
resulting arrays into CLIP batches; a single writer stores the vectors. Because
each stage has its own bounded queue, disk latency, CPU decode cost and GPU time
overlap instead of running in sequence, and back-pressure keeps memory flat no
matter how big the tree is. `--io-workers` sizes the reader pool. Captions use
the same idea: `--describe-batch N` sends N frames to the vision model per
forward pass instead of one, which is the single biggest win when describing a
large tree (default 1; raise it while watching memory).

**Picking the flags from measurements.** `about bench` measures the machine
instead of guessing — it times disk reads, CPU decoding and CLIP batches in
isolation, then runs several real configurations end to end through the
pipeline and reports which one was fastest:

```bash
.venv/bin/media-match about bench                 # synthetic corpus, ~30 s
.venv/bin/media-match about bench ~/Pictures      # against your real files
```

Nothing is indexed and no file is touched. It prints, per configuration,
throughput and the share of wall time spent in the GPU, and ends with a
concrete recommendation:

```
fastest measured: --batch 16 --io-workers 4 --workers 8   (31 img/s, 38% of wall time in the GPU)
recommended:     --batch 8  --io-workers 2 --workers 4   (cheapest of the tied configurations)
at 29 img/s, 20,000 file(s) in this tree takes about 11 min 30s on this machine
```

When several configurations measure the same it says so and recommends the
cheapest of them rather than the nominal winner: on a small corpus the
run-to-run spread (~10% here) is larger than the gap between neighbouring
settings, and picking the nominal winner would dress up a coin flip as a
measurement. Raise `--files` and `--repeat` to separate them.

The default corpus is synthetic on purpose — no photos needed, identical every
run so numbers stay comparable between runs and machines. Pass a folder when
your library does not resemble the built-in shapes (12MP phone photos down to
thumbnails).

Images also record EXIF **capture time, camera and GPS**, so you can search by
date (`--since`/`--until`) or camera, `stats` reports the captured date range,
and `duplicates --prefer date` marks the newest capture as the best copy (the
default picks the largest).

**Videos** are indexed by sampling keyframes (~1 fps, capped at 120 for long
clips) with `ffmpeg`, then running those frames through the same CLIP + pHash
layers. Keyframes are sampled on a fixed time grid, so duplicate copies line up
frame-for-frame and are matched by *aligned* comparison (O(n)) rather than
all-pairs. The scan prepares frames on a thread pool that feeds the CLIP
batcher, so image and video work share one pipeline and the GPU stays busy
(measured GPU-busy time ~73% → ~99%; see `docs/video-spike.md`).

**Tag refinement** turns the loose VLM keywords into a tidy vocabulary.
`refine` lowercases, singularizes (with irregular plurals), merges obvious
synonyms (`guy`→`man`, `bike`→`bicycle`) and drops filler, writing canonical
tags into `keywords` while keeping the originals in `raw_keywords`. Every tag is
also bucketed into a **facet** (person/animal/object/scene/food/plant/text/
activity/color). `classify` gives each image a **type** via zero-shot CLIP:
the category prompt sentences are embedded once, and the image is labeled with
the closest category — no extra model or training. `analyze` runs `describe`,
fills any missing embeddings, then `classify` and `refine`; when you only want
one stage, `describe`, `classify` and `refine` are separate commands.

**People clustering** takes every photo whose facet is `person`, embeds its CLIP
vector, and links photos whose cosine similarity clears a threshold, so
same-looking people group together. It is honest about its limits: CLIP groups
*similar photos of a person in a similar shot*, not verified identities (that
needs a face-embedding model). `people --label N=Name` names a cluster and
`search --cluster Name` lists it.

**Watching a long stage run.** On a terminal, `scan`, `analyze`, `describe`,
`embed`, `classify`, `check` and the inventory/check folded into `bootstrap`
draw a live progress display — a two-line bar where there is a per-item count,
or a spinner for an all-pairs walk — instead of periodic "preparing [n/total]"
lines:

```
⠹ indexing     14,208/20,000  [█████████████░░░░░░░░]  71%  186/s↗  eta 0:50
now  Photos/IMG_4471.jpg, Photos/IMG_4472.jpg   ring 1.0GB/1.0GB  elapsed 1m16s  cpu 38.2s  gpu 11.4s (30%)  read 1.2GB
```

The rate and ETA are **not** a lifetime average. They are extrapolated from the
last 60 seconds of completed items, like the "about 40 seconds remaining" in
an OS copy dialog: a stage that starts fast and then hits a folder of huge
videos slows down instead of keeping the original promise. The arrow beside
the rate shows whether it is speeding up (`↗`) or slowing down (`↘`). The
spinner changes while work is moving; when the stage stops, it becomes `✓` (or
`!` when files failed) and the ETA is removed.

The counters are there to tell you whether to wait or interrupt:

- **ring** — how full the read buffer is. **Full** means the disk is ahead of
  the CPU and more `--io-workers` will not help. **Empty** means the readers
  are the bottleneck and it will.
- **cpu** — CPU-seconds across all threads. Rising faster than wall time means
  the workers really are parallel; flat means more threads will not help.
- **gpu** — time inside embedding calls, as a percentage of wall time. Low
  GPU share with a full ring is exactly the "GPU is idle" case the ring buffer
  exists to fix.

During `describe` the same bar reads the second line as `window 6/8`: how many
frames the CPU has decoded ahead of the caption model. A **full** window means
the GPU is the bottleneck and `--describe-workers` will not help; an **empty**
one means the captioner is waiting on decodes and it will.

**Models are front-loaded.** Every stage loads the weights it needs before its
bar starts, with `loading <model> ...` and `model ready in ...` around the
first-run download. `scan` and `analyze` load CLIP before indexing; `analyze`
then releases CLIP while the caption model runs, and reloads it before the
embedding/classify bars. `scan`, `analyze`, `describe`, `search`,
`similar --image`, `embed` and `classify` reuse the model recorded in the index
(override with `--clip-model` / `--model`) instead
of silently loading a different vector space. `embed` refuses to add vectors
from a different model unless `--recompute` replaces the old ones, so a search
can never compare two unrelated embedding spaces. The same load can be animated
without fighting a full bar. Grouping steps (`similar`, `duplicates`, `people`)
use a spinner rather than a percentage, because they run as one all-pairs
operation with no natural per-item count.

`--no-progress` turns the display off (implied when stderr is not a terminal,
so piped output and CI keep one-event-per-line logs). `MEDIA_MATCH_NO_PROGRESS=1`
does the same from the environment. With the bar off, progress lines still
appear at 5% steps and at least every 10 seconds — naming the file being read
or decoded, or `embedding` while a GPU batch is in flight — so one slow video
cannot make a large scan look hung.

## Configuration

Defaults you usually repeat can live in `~/.config/media-match/config.toml`. An
explicit command-line flag always wins, then the config, then the built-in
default:

```toml
[media-match]
clip_model = "mlx-community/clip-vit-base-patch32"
workers = 8
threshold = 8
```

To keep paths out of the index, add a `.media-matchignore` in the scanned root
(globs, one per line, `#` comments). Matching is against the path relative to
the root and its basename, so directory entries and bare names both work:

```
node_modules/
*_export/
*.tmp
```

Ignored paths are skipped by `scan` and dropped by `scan --prune`.

## Usage

```bash
# 0. optional first pass over a messy tree: inventory it, clean up duplicate
#    and non-media files, and check loadability. Nothing moves without --yes.
#    The same check as 'check' runs by default and offers to re-encode
#    truncated or quarantine corrupt files (asks first in a terminal).
.venv/bin/media-match bootstrap ~/Pictures
.venv/bin/media-match bootstrap ~/Pictures --prune            # trash exact dupes
.venv/bin/media-match bootstrap ~/Pictures --media-only       # drop non-media
.venv/bin/media-match bootstrap ~/Pictures --media-only --fix-extensions
#    move non-media files to a folder instead of trashing them (layout kept)
.venv/bin/media-match bootstrap ~/Pictures --media-only --move-to ~/non-media --yes

# 1. index a photo tree: content hash + pHash + CLIP embeddings (~500 img/s)
.venv/bin/media-match scan ~/Pictures

#    the built-in guide (every command, every flag, examples)
.venv/bin/media-match help              # all commands + flags + an example each
.venv/bin/media-match help scan         # one command in full
.venv/bin/media-match scan help         # the same page — all three forms match
.venv/bin/media-match scan --help

# 1a. huge library? build the index in two steps. The stat-only quick pass
#     writes one basic row (path/size/mtime, stable id) per media file —
#     no decoding, no GPU, seconds for 100k files — and a normal scan then
#     fills the rows in, in id windows if you like
.venv/bin/media-match scan ~/Pictures --quick
.venv/bin/media-match scan ~/Pictures --start-id 1 --stop-id 1000
.venv/bin/media-match scan ~/Pictures --startid 1001 --limit 1000  # next slice

# 2. complete analysis pass: caption everything that has no caption, fill in
#    missing CLIP embeddings, type each image, then refine captions/keywords
#    into canonical tags and facets. All stages run by default.
.venv/bin/media-match analyze ~/Pictures --video

#    ... or run one stage alone. 'describe' must run before 'refine', because
#    refinement builds tags from the captions.
.venv/bin/media-match describe ~/Pictures --video
.venv/bin/media-match classify ~/Pictures
.venv/bin/media-match refine ~/Pictures

# 3. find photos by person / object / free text (CLIP vector search)
.venv/bin/media-match search ~/Pictures "woman red jacket"
.venv/bin/media-match search ~/Pictures --object bicycle
.venv/bin/media-match search ~/Pictures "birthday cake" --fts   # caption search

#    by capture date / camera (EXIF; falls back to file mtime)
.venv/bin/media-match search ~/Pictures --since 2021-06 --until 2021-12
.venv/bin/media-match search ~/Pictures --camera iPhone

# 4. duplicate groups; best-resolution version marked with *
.venv/bin/media-match duplicates ~/Pictures
.venv/bin/media-match duplicates ~/Pictures --json        # machine-readable
.venv/bin/media-match duplicates ~/Pictures --threshold 4 # stricter pHash

# 5. semantic near-duplicate groups (CLIP cosine similarity)
.venv/bin/media-match similar ~/Pictures
.venv/bin/media-match similar ~/Pictures --image /tmp/stray.jpg  # one image

# 6. review duplicates and move rejected copies to the OS Trash.
#    Opens a visual bar UI with the key legend pinned at the top:
#      space = keep the file under the bar (unselects the group's others)
#      a     = keep this whole group       A = keep every file
#      v     = Quick Look the file       p = open it in Preview.app
#      x     = trash this file now (y/n) enter = trash all unkept files (y/n)
#      e     = trash only the decisions made so far — every group up to and
#              including the bar's group (y/n) — then keep reviewing
#      q/esc = quit; asks y/N first if files are still marked for the Trash
#    The algorithm's best copy of each group starts selected. Without a
#    terminal it falls back to line-based prompts.
.venv/bin/media-match clean ~/Pictures
.venv/bin/media-match clean ~/Pictures --dry-run  # preview the plan
.venv/bin/media-match clean ~/Pictures --yes      # accept all suggestions

# 6b. same-named folders: merge 2019/christmas, 2020/Christmas, 2021/CHRISTMAS
#     into one copy. The shallowest copy is suggested as the destination;
#     each same-named file is decided with r/R=replace, n/N=rename,
#     s/S=skip, c=compare (size, EXIF, video facts), q=quit. Nothing moves
#     until the final confirmation; quitting offers to keep the folders
#     already finished. --collapse instead gathers whole folders into
#     <root>/<Name>_collapsed/ as <Name>_1, <Name>_2, ... without merging files.
.venv/bin/media-match folders ~/Pictures --list
.venv/bin/media-match folders ~/Pictures --name christmas
.venv/bin/media-match folders ~/Pictures --dry-run --rename
.venv/bin/media-match folders ~/Pictures --collapse
.venv/bin/media-match folders ~/Pictures --rename --yes   # keep both copies
.venv/bin/media-match folders ~/Pictures --replace --yes  # mv -f

# extras
.venv/bin/media-match tags ~/Pictures    # keyword counts from captions
.venv/bin/media-match stats ~/Pictures   # index, models, coverage
.venv/bin/media-match embed ~/Pictures   # backfill CLIP embeddings only
.venv/bin/media-match export ~/Pictures --format json --out index.json

# 7. browse the tags/facets and image types produced by analyze
.venv/bin/media-match tags ~/Pictures --facets       # tags grouped by facet
.venv/bin/media-match tags ~/Pictures --types        # type counts
.venv/bin/media-match search ~/Pictures --type selfie

# 8. group photos of the same person and name the groups
.venv/bin/media-match people ~/Pictures              # cluster person photos
.venv/bin/media-match people ~/Pictures --label 3=Alice
.venv/bin/media-match search ~/Pictures --cluster Alice

# videos — pass --video to index/search/group/review video files
.venv/bin/media-match scan ~/Movies --video        # keyframes + CLIP (~1 fps)
.venv/bin/media-match search ~/Movies "dog on a beach" --video
.venv/bin/media-match duplicates ~/Movies --video  # re-encodes, across resolution
.venv/bin/media-match similar ~/Movies --video     # same-subject video groups
.venv/bin/media-match clean ~/Movies --video       # same review UI as images

# tuning the scan pipeline — the defaults suit most trees
.venv/bin/media-match scan ~/Pictures --io-workers 4    # disk reader threads
.venv/bin/media-match analyze ~/Pictures --describe-batch 6  # caption 6/forward pass
```

Damaged files are reported by name, not as a wall of Pillow warnings. `scan`
groups what it could not index by cause and points at `check`; `check` then
names each file with the reason and what can be done about it:

```
$ media-match check ~/Pictures
2 ok, 1 truncated, 1 corrupt, 1 notable
  truncated: IMG_0042.jpg
      truncated file — 640x480 header intact but the pixel data ends early; 'media-match check' can re-encode it
  corrupt:   2019-07/scan.mov
      ffmpeg could not read it: moov atom not found
  notable:   Sunset.mpo
      malformed MPO container, read as a plain JPEG — the image itself is fine
```

`truncated` is repaired by re-encoding (the original is kept as
`<name>.truncated`) and `corrupt` is moved to `.media-match-quarantine` — both
only with `--yes` or a confirmation. `notable` files are never modified: they
load correctly, so acting on them would damage good photos.

> **Quote paths that contain spaces or shell metacharacters** (`&`, `$`, `;`,
> quotes, `…`). The program handles them fine, but an *unquoted* `&` makes the
> shell split the command in two, so it fails with "no such file or directory"
> before it ever reaches us:
>
> ```bash
> media-match scan "/Users/me/_Private/Pictures/Timh & Dung"   # ✓ quoted
> media-match scan /Users/me/_Private/Pictures/Timh & Dung      # ✗ shell splits on &
> ```

Example `duplicates` output:

```
Group 1 (2 files)
  * ~/Pictures/beach_original.jpg  (4032x3024, 12.2MP) [best]
    ~/Pictures/beach_thumb.jpg  (150x100, 0.0MP) hamming=0
```

### Folder consolidation

`folders` is the same idea one level up: it finds directories that share a
name regardless of case — `2019/christmas`, `2020/Christmas`,
`2021/CHRISTMAS` — and merges their files into the copy closest to the root.
`--name NAME` narrows discovery to names containing NAME, like
`find -type d -iname '*NAME*'`; `--list` only reports.

Example `folders --list` output:

```
Group 1/1 — christmas (3 folders)
  [dest*] 2019/christmas  (12 files, 48.2 MB)
          2020/Christmas  (8 files, 31.0 MB)
          2021/CHRISTMAS  (15 files, 60.1 MB)
  * suggested destination (shortest path)

1 group(s), 3 folders — 2 redundant folder(s)
```

During the review, each conflict at the same relative path is one prompt; the
two sides are shown with their size and modification time, and `c` adds EXIF
or video facts:

```
  conflict  photo.jpg
    destination  2019/christmas/photo.jpg  (2.4 MB, modified 2020-12-24 18:31)
    source       2021/CHRISTMAS/photo.jpg  (3.1 MB, modified 2021-01-02 09:12)
  [r]eplace [R]eplace all [n]ame [N]ame all [s]kip [S]kip all [c]ompare [q]uit >
```

Nothing is moved until the final confirmation; quitting asks whether to apply
the folders already finished and excludes the open one. `--rename --yes` keeps
both files, `--replace --yes` is the explicit `mv -f`, and plain `--yes`
skips conflicts rather than guessing. `--collapse` is the non-destructive
alternative: keep the destination where it is and gather the other folders
into `<root>/<Name>_collapsed/` as `<Name>_1`, `<Name>_2`, … without touching
their contents.

Exit status is `0` when the run completed, `1` when the user declined a
confirmation, a folder could not be read, or a move failed, `2` for a bad
invocation, and `130` for `Ctrl-C`. Discovery is all-or-nothing: an unreadable
directory is named and nothing is changed, so a merge never acts on half a
tree. A move that fails is reported with its OS reason and the rest continue.
The stale-index line is printed only when an index actually exists.

### Errors

A mistake is answered with one line on stderr, never a stack trace: a
misspelled or non-directory root prints `No folder at <path>.`, a `--db` in a
folder that does not exist (or a file that is not a database) prints
`cannot open the index database at <path>: <reason>`, and a failed write such
as `export --out` into a missing directory prints the OS reason and the path.
Exit status is `2` for a bad invocation or an index that cannot be opened, `1`
for a missing index or a failed read/write, and `130` for `Ctrl-C`. Unexpected
internal errors still print a traceback — those are bugs, and hiding them would
make them harder to report.

#### ID windows

`--start-id N` / `--stop-id N` (aliases `--startid` / `--stopid`) select an
inclusive window of index rows on every command that reads media rows: `scan`,
`analyze`, `describe`, `embed`, `classify`, `refine`, `search` (including
`--type` and `--cluster`), `similar`, `duplicates`, `clean`, `export`,
`export-metadata`, `import-metadata` and `clear-metadata`. Rows outside the
window are never touched. `files.id` and `videos.id` are independent
sequences; the same numeric window applies to each table separately. A window
selects indexed rows only — run `scan --quick` first to give every file an id. `--start-id 1001 --limit
1000` analyzes the next slice; `--start-id 353 --stop-id 905` is exactly that
range. `--prune` always reconciles the whole index even when a window is set.
Commands that do not take a window, and why: `restore` (trash batches, not
media ids), `bootstrap` (its own re-numbered table), `people` (rebuilds every
cluster, so a partial run would erase the rest), `tags`/`stats`/`info`
(whole-index aggregates).

Basic rows from `--quick` carry no hashes, so they never enter duplicate
grouping or CLIP search until a normal `scan` or `embed` fills them in.

All commands take `--db` to override the index location. `root` defaults to
the current directory. Supported image formats: JPEG, PNG, WebP, GIF, BMP,
TIFF, HEIC/HEIF. Supported video formats (with `--video`): MP4, MOV, M4V, AVI,
MKV, WebM, MPG/MPEG, WMV (anything `ffmpeg` can decode). Audio formats (MP3,
WAV, FLAC, AAC, OGG/OGA, M4A) are recognized by `bootstrap` and kept by
`--media-only`, but audio analysis is not implemented yet — see
[`docs/FEATURE-audio.md`](docs/FEATURE-audio.md).

Default models are the smallest viable ones; for better accuracy use
`--clip-model` / `--model` with any MLX-converted checkpoint, e.g.
`--model mlx-community/Qwen2-VL-2B-Instruct-4bit`.

## Phase 1

Analyze all image files in a folder with a vision agent, classify the images
so that it is easy to find a certain person, an object and identify
duplicates.

This should work across resolution, so that accidentally saved thumbnails are
identified as duplicates and grouped with their primary file that should have
a better resolution.

## Phase 2 (video)

The same as Phase 1, but on video files: find videos by person/object content,
group duplicates and re-encodes across resolution, and identify the best
version. Each video is reduced to ~1 keyframe per second (capped for long
clips), embedded with CLIP for search and matched by keyframe pHash for
grouping. See `docs/video-spike.md` for the sampling and matching design and
the scan-pipeline measurements.

Videos need `ffmpeg` and `ffprobe` on `PATH`. A video the pipeline cannot read
is reported with ffmpeg's own reason ("moov atom not found", and so on), not
with an image error — check `media-match check --video` on the same folder to
separate broken files from a missing tool.

## Goal

The goal is to group images of different people and objects together and to
be able to find the best version of an image that might be duplicated in the
tree the program is working on.
